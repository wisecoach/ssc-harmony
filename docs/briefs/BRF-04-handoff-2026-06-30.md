## 二、v1 被动池（已编译部署，设计错误，需回退）

### 已部署的错误代码

v1 被动池实现在远程 `bin/harmony` 中（编译于 2026-06-30 00:03 和 18:18），包含：

| 错误设计 | 当前实现 | 正确做法 |
|:---------|:---------|:---------|
| 被动池在每个 shard 的 retryScheduler 上 | `passivePool map[txHash]*passivePoolEntry` | 只需 `map[txHash]struct{}` 做标记 |
| RetryCommit 检测到 OnChain 锁冲突→直接进被动池 | `stateDB.CheckLock` 失败时 `AddToPassivePool(tx, lockedKeys)` | RetryCommit 不该管被动池，只返回 Locked=false |
| chainNextSim 扫被动池唤醒 | `scanPassivePool` + `moveToActivePool` | 唤醒走 RetrySignal 路径，不靠 chainNextSim |
| OnBlockCommitted 检查被动池超时 | expiredPassive 检查 + closeTransaction | v2 不需要 |

### 实验验证

用错误二进制跑了一次实验，被动池机制**确实被触发了**（80 笔进池，25 笔被唤醒），但设计方向本就不对：

- **进被动池**: 80 笔
- **唤醒**: 25 笔（31%）
- **retryCommit failed**: 559（比之前的 1129 降了 50.5%）
- **提交率**: 80.7%（比之前的 87.4% 降了——因为更多 tx 进了被动池没被唤醒）

## 三、v2 被动池设计方案（待实现）

### 核心流程

```
分片角色:
  A = 发现锁解锁→发 RetrySignal 的分片
  B = 链上锁冲突的分片
  O = Origin Shard（发起 retry）

流程:
  1. A 发现锁解锁 → RetrySignal → O
  2. O 广播 RetryCommit → A, B
  3. A: TryLock OK → Locked=true
  4. B: TryLock OK → stateDB.CheckLock → 链上锁冲突 → Locked=false
  5. O 收到 B 失败 → O 通知 A: 进被动池
  6. A 把 tx 移入 passivePool → 停止每块 poll
  7. B 的锁释放（SimTx CR）→ B 的 chainNextSim 触发
  8. B → RetrySignal → O
  9. O 广播 RetryCommit → A, B
  10. A 收到 RetryCommit → 出被动池 → Locked=true
  11. B: 这次 OK → Locked=true
  12. 全部 true → TriggerReSimulation
```

### 关键设计点

| 维度 | v2 做法 |
|:-----|:--------|
| 被动池位置 | shard A（发 RetrySignal 的那个），不是 origin 不是 B |
| 进入时机 | O 收到 B 的 Locked=false→通知 A 进 |
| 唤醒机制 | B 锁释放→chainNextSim→RetrySignal→O→RetryCommit→A 收到→出池 |
| 被动池功能 | 只是 `map[txHash]struct{}`——标记"别 poll 了" |
| PoolTimeout | 需要记录 enterBlock，超时 close（与 v1 类似但更简单） |

**不需要修改的现有逻辑：**
- `chainNextSim` 不改——它照常发 RetrySignal
- `RetryCommit` 不改锁竞争逻辑——只加开头检查被动池
- `stateDB.CheckLock` 不改——它只返回 Locked=false

详见 `docs/A09-active-passive-retry-pool.md`（v2 版本）。
