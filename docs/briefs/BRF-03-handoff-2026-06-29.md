## 二、当前发现的核心问题：毒性循环

### 现象

即使所有已知 bug 修完，**高冲突场景下仍有 unfinished 交易**。当前参数 `MaxRetriesTotal=3` 能截断循环（3 次 retry 后 close），但每笔 retry 都在浪费时间，且 blocking 了低优先级交易。

### 根因分析

**三层锁架构中存在跨层优先级失配：**

```
TempLockView（链下, 分片本地）                  stateLockManager（链上, 分片本地）
=============================                  =================================
tempWriteLocks（支持 Wound-Wait）               lockedStates（不可 Wound）
  ├─ 高优先级可以踢低优先级 ✅                      ├─ 锁了就是锁了，谁都没法踢 ❌
  └─ 只看到本分片 ❌                              └─ 只看到本分片 ❌
```

**毒性循环流程：**

```
高优先级 tx A（nonce=0, origin shard 0）的 RWSet 包含：
  - shard 0 的 key K1（本分片，可 Wound）
  - shard 1 的 key K2（远端分片，on-chain 锁中）

每块重复：
  OnBlockCommitted:
    CanLock(txA, [K1,K2]) → tempWriteLocks: K1/K2 都空闲 → true ✅
    （远端 shard 1 上 K2 的 on-chain 锁 ❌ 看不见）

  TryLockWithPriority:
    K1 ← tx B 拿着 → canWound? 是 → 踢掉 B ✅
    K2 → 空闲 → 拿锁
    → 拿到全部 TempLock ✅

  模拟执行:
    shard 0: K1 Patch → OK
    CXT→shard 1: stateDB.GetState(K2)
      → Lockable(baseSnapshot) → K2 被 SimTx C 锁了
      → ErrLockConflict_OnChain ❌

  AddToRetry:
    GarbageCollect → 释放 TempLock
    → 放回 retryPool（仍然是最高优先级）

  结果：
    tx A: 每次都能赢 TempLock，但每次都在远端链上锁失败
    tx B: 被 tx A 反复 Wound，永远拿不到锁 😢
    两者都无进展 → 烧完 MaxRetriesTotal=3 → close(超限)
```

### 关键代码位置

| 组件 | 文件 | 关键行 | 做了什么 |
|------|------|:------:|---------|
| CanLock 盲区 | `ssc/temp_lock_view.go` | 180-200 | **只查 `tempWriteLocks`**，不查 `stateLockManager.lockedStates` |
| TryLockWithPriority 盲区 | `ssc/temp_lock_view.go` | 66-151 | Wound 也只查 tempWriteLocks，不知道远端链上锁 |

## 三、修复方案：被动 Retry Pool

### 设计思路

把 retry 从 **Poll-based（每块主动竞争）** 改成 **Event-driven（远端通知唤醒）**。

### 核心流程

```
RetryCommit 失败:
  ↓
分析失败原因:
  ├─ ErrLockConflict_OnChain（远端分片链上锁冲突）
  │   → 解析冲突 key → 移入 passivePool
  │     （记录 waitingKeys + 进入时的 blockNum）
  │
  └─ 其他原因（VM 执行错误/本地锁冲突等）
      → 放回 active pool（当前逻辑不变）

chainNextSim 触发时（SimTx 提交）:
  ↓
  扫描 passivePool:
    对于每笔 tx: 检查所有 waitingKeys 是否已被释放
      ├─ 全释放 → 移回 active pool
      └─ 仍有未释放 → 继续等待

PoolTimeout 统一回退（主动+被动池都适用）
```

### 关键设计点

**1. 何时移入被动池**

只针对 `ErrLockConflict_OnChain`——必须是远端分片的链上锁冲突。本地链上锁冲突或链下 TempLock 冲突不移入。

区分依据：`state_locker.go` 返回的 error 已经带了 `ErrLockConflict_OnChain` vs `ErrLockConflict_OffChain`，可以直接用。

**2. 等待哪些 key**

从失败的 `SimulationCallStates` 中提取 LockedKeys（已在 `callState.LockedByOtherTx` 中记录），记录到 `waitingKeys`。

**3. 如何唤醒**

`chainNextSim` 的现有匹配逻辑（`dependsOn` 检查 WriteSet 交集）可以直接复用——在扫描 active pool 的同时扫描 passive pool。

**4. 多 key 依赖**

如果 tx 依赖多个远端分片的不同 key（更常见的情况），`waitingKeys` 是所有 key 的并集。**所有 key 都释放时才能唤醒**。

**5. 超时兜底**

`PoolTimeout` 直接作用于 passive pool——进入 passive pool 时记录 `blockNum`，超时后 close。

### 优势

| 对比 | 当前 Poll-based | 被动池 Event-driven |
|------|---------------|-------------------|
| 高优 tx 行为 | 每块 wound 低优 tx → 远端失败 → 循环 | 进入被动池，**不竞争不 wound** |
| 低优 tx 机会 | 被反复 wound，**永无机会** | 高优 tx 不在 active 池，低优可以正常竞争 ✅ |
| 每次 retry 开销 | 模拟执行 + 跨分片 CXT（浪费） | **0 开销**，直到被通知唤醒 |
| 唤醒时机 | 每块 CanLock | **锁释放时才唤醒** |
| 通知通道 | 无 | chainNextSim ✅ 已存在 |

### 数据结构和接口

```
// 新增
type passivePoolEntry struct {
    RetryTx     *api.RetryTx
    WaitingKeys map[api.LockKey]struct{}  // 等待中的 key 集合
    EnterBlock  uint64                    // 进入被动池的区块号
}

type retryScheduler struct {
    // 已有
    retryPool    map[common.Hash]*api.RetryTx    // 主动池
    // 新增
    passivePool  map[common.Hash]*passivePoolEntry // 被动池
}
```

## 四、后续开发步骤

### Step 1: 失败原因分类逻辑

- 在 `RetryCommit` 失败路径上，从 `callState.LockedByOtherTx` 提取 LockedKeys
- 判断哪些是远端分片的链上锁冲突

### Step 2: 被动池数据结构

- 新增 `passivePool` 字段 + `passivePoolEntry` 结构体
- `AddToPassivePool()` / `RemoveFromPassivePool()` / `IsInPassivePool()`

### Step 3: chainNextSim 扫描被动池

- 在 `chainNextSim` 已有的 `dependsOn` 匹配逻辑中，同时扫描 `passivePool`
- 匹配的 key 从 `waitingKeys` 中移除
- `waitingKeys` 为空 → 移回 `retryPool`

### Step 4: 超时兜底

- `OnBlockCommitted` 中扫描 `passivePool`，检查 `EnterBlock + PoolTimeout 是否过期`
- 超时 → close transaction

### Step 5: 实验验证

- `MaxRetriesTotal=3` + 被动池 → 预期不再有「3 次 retry 全部浪费」的情况
- unfinished 交易应该显著减少
