## 三、待解决问题

### 1. `download_log` 不生效

`test_single` 的 `download_log` 步骤没把验证器日志拉到 `~/go/src/github.com/harmony-one/logs/harmony-sscc/`。导致 data_handler 只能处理客户端数据，无法解析 SSC 日志中的 `retry_limit_exceeded` 等事件。

**排查方向：** `test/dev_deploy.sh:download_log` 中 `$WORK_DIR` 路径是否正确。

**临时方案：** 手动从节点服务器抓日志：
```bash
ssh -p 10022 zjnu@10.7.95.200  # 或其他节点
# 查看 ssc-validator*.log 或 log-*.log
```

### 2. PoolTimeout 导致的超时

当前 `PoolTimeout=5`，Sp1=5 且重试限制收紧后，大量交易因超时（不是回滚）被关闭。`Shard 1` 超时高达 74 笔。

可能原因：PoolTimeout 和 Sp1 一样都是 5，但 pool timer 和 sp1 timer 的触发时序可能导致不必要的超时。

**调整方向：** `PoolTimeout` 适当比 `Sp1` 大（如 Sp1=5, PoolTimeout=8），给交易更多时间完成跨 shard 流程。

### 3. 日志文件被旧日志覆盖

`download_log` 写到固定路径，旧日志不删的话 data_handler 可能处理旧数据。需每次实验前清空目录：
```bash
rm -rf ~/go/src/github.com/harmony-one/logs/harmony-sscc/shard=*_delay=*_rate=*/
```

### 4. data_handler 的 retry_limit_exceeded 追踪

已在 `data_handler.py` 添加了：
- `get_validator_ssc_log_event` 中解析 `AddToRetry: max total retries exceeded` 和 `ReasonMaxOnChainRetriesExceeded`
- `handle_tx` 中处理 `retry_limit_exceeded` 事件
- `compute_summary` 中统计并输出 `retry_limit_exceeded` 数量

依赖 `download_log` 修复后生效。
