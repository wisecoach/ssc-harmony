## 一、发现并修复的 3 个 Bug

### Bug 1：Simulator.SetState 没查 Patch 路径

**场景**：链式依赖交易重试时，VM 执行 `SetState` 调用 `db.GetState` 触发 `stateDB.locker.Lockable`，撞上 stateLockManager 中上游 SimTx 的未释放锁。

**根因**：`Simulator.GetState`（Line 832）实现了 Patch 路径（先查 ChainPatchRef/ChainPatch 再调 db.GetState），但 `Simulator.SetState`（Line 918）没有——直接调 db.GetState 读当前值。

**修复**：`SetState` 加入 Step 0（ChainPatchRef）+ Step 1（ChainPatch），Patch 命中时直接从 Patch 取值，不走 `db.GetState`。

**修改**：`ssc/simulator.go`

### Bug 2：Wound 后误调 closeTransaction 导致链上锁泄漏

**场景**：交易在 `CommitSimulation` 中被 Wound → 调了 `closeTransaction` → delete txStates + 标记 finishedTxs。但此时 `CommitSimulation Multicast` 已在路上，related shard 收到后提交 SimTx → `stateLocker.Commit()` 合并锁到 `stateLockManager.lockedStates` → 锁无人清理 → `LOCK_STALE` 持续出现。

**根因**：Wound 后的交易应放回 retryPool 重新竞争（设计文档 A06 §6.4），不应调 `closeTransaction` 终结。

**修复**：Wound 分支只 `Release` PatchPool，不调 `closeTransaction`。同时在 `temp_lock_view.go` 的 `TryLock` 中用 `Priority{FirstSimBlock: MaxUint64, TxHash: txHash}` 避免空 Priority 无敌锁。（注：后来 `TryLock` 又改回了 `Priority{}`，因为该函数已被废弃不再使用。）

**修改**：`ssc/impl.go`、`ssc/temp_lock_view.go`

### Bug 3：SimulationNum 优先级军备竞赛导致饿死

**场景**：最高重试 74 次的交易仍未 close。所有竞争同一 HotKey 的交易的 `SimulationNum` 同步增长，差距无法拉开。

**根因**：优先级 `(SimulationNum >, Nonce <, OriginShardID <)` 中 SimulationNum 权重最高，但所有交易同步重试。

**修复**：先后尝试了 `FirstSimBlock`（首次模拟区块高度）、`Nonce > OriginShardID > TxHash`（纯静态，当前方案）。最终方案为 `Nonce > OriginShardID > TxHash`——全是静态值，不涉及区块高度或重试次数。

**修改**：`ssc/api/types.go`、`ssc/retry_scheduler.go`、`ssc/simulator_leader.go`

## 二、TempLockView 设计演进

### 阶段 1：TempLockTryLock（原始设计）

首次模拟结束后批量获取 TempLockView 锁。
- 问题 1：`Priority{}` 创造无敌锁（`TxHash=0x0`）
- 问题 2：单 shard 预检查，无法覆盖 related shard
- 问题 3：Wound 路径不清理锁

### 阶段 2：GetState/SetState 逐 key 上锁

模拟执行期间逐 key 调用 `TryLockWithPriority`。
- 问题：对单个 key 上锁，缺少原子性。部分 key 锁住后遭遇冲突无法回滚，导致锁泄漏
- 尝试：在 `AddToRetry` 中加入 `GarbageCollect` 作为回滚机制

### 阶段 3：回归无锁首次模拟 + 泄漏兜底（当前方案）

- 首次模拟不获取 TempLockView 锁（和原始设计一致）
- GetState/SetState 无锁，`AddToRetry` 中 GarbageCollect 清理残留
- `impl.go` Wound 路径 GarbageCollect 作为安全网
- `retryCommit` 通过 `TryLockWithPriority` 正常上锁

## 四、残留问题

**267 笔 unfinished 交易卡在 `chainNextSim` 调度器活锁中。**

最后一条活动日志：`chainNextSim: skipped due to reserved state conflict`

`chainNextSim` 负责在区块提交时为 retryPool 中的交易预留槽位。当所有剩余交易的 WriteSet 重叠时，调度器无法为它们分配不同的区块，全部被跳过，之后调度停止。

这不是 TempLockView 或 Priority 的问题，属于 `chainNextSim` 调度器自身的调度死锁。超出本次 session 范围。
